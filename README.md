# Thapar DigiLocker — Web Portal + Desktop App

## Open from anywhere

The browser app is in `web.py`. It reuses `locker.py` and `models.py`, with student,
faculty and gate staff workspaces, PDF certificates, exams and marks, personal
timetables, e-ID enrollment, simulated gate verification, and gate history.
The public university timetable and academic calendar work without signing in.
The original desktop app remains available with `python app.py`.

### Run the website locally

```powershell
python -m pip install -r requirements.txt
$env:SEED_DEMO = "1"
python web.py
```

Open **http://127.0.0.1:5000**. Demo credentials are listed below and on the login
page when demo mode is enabled. On macOS/Linux use `SEED_DEMO=1 python web.py`.
For the production server run `python serve.py` instead. By default the web app
uses its own `data/locker.sqlite3`; it does not copy your desktop records.

### Deploy from GitHub to Render

GitHub stores the project; Render runs the Python app and gives you an HTTPS
website link. GitHub Pages cannot run this server or SQLite backend.

1. Push this folder to a GitHub repository.
2. In [Render](https://dashboard.render.com/), select **New → Blueprint**, connect
   the repository and use the included `render.yaml`.
3. Review the hosting cost before creating the service. The blueprint requests a
   **paid Starter web service and a 1 GB persistent disk** so your database,
   certificate files and photos survive restarts and redeploys. It does not use
   the ephemeral filesystem of a free service.
4. Enter unique `ADMIN_PASSWORD` and `GATE_PASSWORD` values (at least 8 characters).
   The initial usernames are `faculty` and `gate`. `SECRET_KEY` is generated by
   Render, secure cookies are enabled, and demo accounts are disabled.
5. Deploy, open the returned `https://…onrender.com` address, and sign in as
   **Admin / Faculty** to create students. Bookmark that link. Your computer can
   be switched off; the host runs the app. Repository changes deploy through
   the connected service.

See [Render Blueprint configuration](https://render.com/docs/blueprint-spec) and
[persistent disks](https://render.com/docs/disks) for current hosting details.
An existing signed-in Render account and approval of its displayed charges are
needed to activate hosting; adding files to GitHub alone does not deploy it.

### Configuration and storage

Set environment variables in your host dashboard or shell; `.env.example` is a
reference, and the app does not automatically load `.env` files.

- `DATA_DIR`: directory for `locker.sqlite3` and uploaded data (stored as SQLite
  blobs). Mount a persistent volume here. Default: `./data`.
- `SECRET_KEY`: long random cookie-signing secret. Required on Render. Local
  runs generate a stable ignored key in the data directory.
- `COOKIE_SECURE=1`: use with HTTPS hosting; keep `0` for localhost HTTP.
- `SEED_DEMO=1`: opt in to known demo accounts on an empty database. Default: `0`.
- `ADMIN_USERNAME` / `ADMIN_PASSWORD`, `GATE_USERNAME` / `GATE_PASSWORD`: provision
  initial staff accounts once. Existing accounts are never overwritten by a
  redeploy or environment-variable change.
- `PORT`: server port, default `5000` (Render supplies its own).

Keep one service instance attached to the SQLite disk. Back up the database
using SQLite's backup API or the provider's disk snapshots. Do not commit live
databases, photos or passwords to GitHub. To migrate desktop records, back up
the desktop database while the app is closed, copy it as
`DATA_DIR/locker.sqlite3` before first startup, and change known demo passwords
before exposing those records online.

The project remains an OOP lab demonstration. Gate image comparison is a
simulation, rather than biometric authentication; use sample identities and
photos. The hosted configuration does not seed publicly known staff passwords.

### Docker (alternative host)

Build with `docker build -t thapar-digilocker .`. Run with a persistent volume
mounted at `/data`, set `SECRET_KEY`, `ADMIN_PASSWORD`, `GATE_PASSWORD`, and publish
container port `5000`. Set `COOKIE_SECURE=1` behind your HTTPS host.


## Before login: campus services

Both quick-access cards now sit **in the white top header beside the TIET logo**, and both open **inside the DigiLocker desktop application** rather than opening an external file.

- **See your timetable:** Enter or select a batch code (such as `2Q1A`, `2C1A`, `1A1A` or `3C1A`). Start typing to filter suggestions. Use **Down / Up**, **Enter**, or the combobox dropdown, or click **View timetable**. You can inspect every weekday with room/instructor information or switch to a Monday–Saturday weekly grid.
- **Academic calendar:** Shows milestones and an embedded scrollable image of the uploaded **Academic Calendar (Odd Sem 2026–27): UG-II, III, IV, PG-II**, with **+ / – / Fit width** zoom controls. It is a one-page calendar. The underlying PDF is also included in assets for traceability, but the app does not open it externally.

### Timetable parsing and accuracy

The supplied `TIME TABLE JULYTODEC2026(1).xlsx` workbook has nine sheets. `build_timetable.py` parses **the eight undergraduate year A/B worksheets** and indexes **503 unique batch codes**. The `assets/timetable_index.json` contains the result and is read directly by `app.py`, so users do **not** need Microsoft Excel or a spreadsheet package to run the app. The original workbook is preserved in `assets/university_timetable_2026.xlsx`.

Each batch maps to its original sheet and lecture/tutorial/practical headers. Sessions are read from the original two-row time slots; horizontally merged lecture cells are resolved for each sub-batch. Room and instructor values are included where the workbook supplies them. If a sheet only says `LAB`, the app retains that label instead of inventing a course name. Some timetable entries list alternate weeks, multiple elective choices or multiple instructors; the app preserves the source text rather than making assumptions. A few fourth-year codes appeared twice in older and newer columns; the populated **July–December** column is selected.

To rebuild the index after replacing the spreadsheet with a workbook of the *same layout*, run:

```bash
python3 build_timetable.py
```

The pre-built index works offline. Do not assume that a new semester's workbook will use the same structure; it may require changes to the parser.

## OOP guide for the viva

The existing three-file structure separates responsibilities:

- `app.py`: `DigiLocker` builds Tkinter screens and handles button clicks.
- `models.py`: domain classes hold data, validate it and describe their behavior.
- `locker.py`: `Locker` checks permissions and reads or writes SQLite records.

### Concepts already demonstrated

- **Classes and objects:** `Locker.login()` creates a `Student`, `Admin` or `GateStaff` object. `Locker.exams()` constructs `Exam`, `Marks` and `MarkSheet` objects from saved rows.
- **Inheritance:** `Student(User)`, `Admin(User)` and `GateStaff(User)` reuse `User.__init__()` and `User.authenticate()`. `Certificate`, `MarkSheet` and `EIDCard` inherit from `Document`. `PhotoVerifier`, `IDVerifier` and `LocationVerifier` inherit from `Verifier`. `DigiLocker(tk.Tk)` inherits window methods such as `mainloop()`.
- **Encapsulation:** `User.__password_hash` is used through `User.authenticate()`. `Marks.__score` and `Marks.__maximum` are read through `Marks.score` and `Marks.maximum`. `EIDCard.number`, `MarkSheet.marks` and `FaceProfile.reference_photo` are also read-only properties. Python's double underscore uses name mangling to discourage accidental access; it is not a security boundary or encryption.
- **Abstraction:** `Document(ABC)` requires `get_details()` and `Verifier(ABC)` requires `verify()`. Their abstract methods specify what concrete subclasses must implement. Neither base class can be instantiated directly.
- **Method overriding:** `Certificate.get_details()`, `MarkSheet.get_details()` and `EIDCard.get_details()` implement the document operation differently. `PhotoVerifier.verify()`, `IDVerifier.verify()` and `LocationVerifier.verify()` implement the verifier operation differently. The user subclasses change the `role` class attribute; they do not override authentication methods.
- **Polymorphism:** `Document.display()` calls `self.get_details()`, which selects the concrete document's implementation. In `Locker.verify_gate()`, `verifier.verify(check)` runs a different check for each verifier object without a type-based conditional.
- **Composition (has-a relationships):** `TimetableEntry` contains a `Course` and an `Instructor`; `Exam` contains a `Course` and an `ExamCentre`; `MarkSheet.__init__()` stores an `Exam` and a `Marks` object. `Locker.__init__()` creates and holds verifier objects. These are object relationships, not inheritance; Python does not enforce exclusive ownership of the contained objects.
- **Parent constructor reuse:** `Certificate.__init__()`, `MarkSheet.__init__()` and `EIDCard.__init__()` use `super().__init__()` to initialize shared document data. `DigiLocker.__init__()` uses it to initialize the Tk window.

### Small Python features worth explaining

- `@property` allows access such as `marks.score` while keeping control inside the class. A property without a setter prevents normal assignment to that property; it does not make an entire object immutable.
- `@staticmethod` is used for operations such as `User.hash_password()` that need no instance state.
- `@dataclass(frozen=True)` supplies ordinary data-class methods, including a constructor, and prevents normal field reassignment. It does not recursively freeze contained objects.
- `Locker.connect()` uses a context manager so repeated database operations consistently commit or roll back and close the connection.
- `__str__()` defines an object's readable text representation; for documents, it delegates to `display()`.

These existing features avoid repeated code. Extra service layers, duplicate authentication methods in each role, and one class for every UI action are unnecessary here.

### Likely viva questions

1. **Why use a `User` base class?** All three roles share account attributes and password authentication, so the common implementation is written once.
2. **Where is runtime polymorphism used?** In `Document.display()` and the verifier loop in `Locker.verify_gate()`; Python chooses the method using the actual object's class.
3. **How is overriding different from inheritance?** Inheritance reuses behavior; overriding gives an inherited operation a subclass-specific implementation, such as `EIDCard.get_details()`.
4. **Why use abstract classes?** They define required operations and prevent construction of incomplete base objects such as `Document` and `Verifier`.
5. **Why keep marks private?** `Marks.__init__()` validates the values, and read-only properties prevent ordinary reassignment that could bypass that validation.
6. **What does `super()` do?** It calls the next implementation in the method resolution order; here, the subclasses use it to initialize their base-class data.
7. **How does composition differ from inheritance?** A `MarkSheet` has an `Exam`, while a `Certificate` is a `Document`.
8. **Why separate the files?** The interface handles widgets, the models represent domain concepts, and `Locker` handles permissions and persistence.
9. **Is the private password attribute enough for security?** No. The code stores a salted PBKDF2 hash and compares derived hashes in `User.authenticate()`; privacy naming alone does not protect passwords.
